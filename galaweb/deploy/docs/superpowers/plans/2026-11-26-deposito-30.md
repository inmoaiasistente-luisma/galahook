# Depósito del 30 % — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let customers book paying 30 % now and 70 % later. The 70 % is collected through an emailed pay
link, with reminders at days −7 and −6 before the trip and an automatic cancellation on the morning of day −5.

**Architecture:**
- One pure module (`server/lib/deposit-policy.js`) holds every rule: eligibility, amounts, dates, sweep
  decision and balance-link token. Every other piece calls it.
- The deposit is the booking's first PaymentIntent (`metadata.kind='deposit'`).
- The balance is a second PaymentIntent created from a tokenized `/saldo` page (`kind='balance'`).
- The existing daily cron (`reminders-run`) also runs the deposit sweep.
- No new Vercel function (11/12 used): balance payment is a mode of `api/create-payment-intent.js`; the
  admin action goes through `admin-router`.

**Tech Stack:** Node serverless (Vercel), Supabase (service role), Stripe PaymentIntents + card Elements,
Resend via `booking-email-service`, plain-node tests (`tests/*.js`, `tests/helpers/fake-supabase.js`).

**Spec:** `docs/superpowers/specs/2026-11-26-deposito-e-inscripciones-design.md` (sections 1–5, 7–10).
The subscribers part (section 6) gets its own plan after this ships.

## Global Constraints

- Deposit = 30 % of `pricing.amountCents` (the total after the discount code): `depositCents = Math.round(total * 30 / 100)`, `balanceCents = total − depositCents`.
- Eligible only if `!tour.requiresQuote && tour.priceCents != null` and `daysUntil(todayInGalapagos(), booking_date) > 30`.
- Dates are fixed at booking, using `shiftYmd`:
  - `balance_due_date = booking_date − 6` (last day to pay, 23:59 Galápagos);
  - `deposit_refundable_until = booking_date − 31`;
  - `balance_refundable_until = booking_date − 16`.
- Sweep, computed from days until the trip:
  - day 7 → email `balance_reminder_d7`;
  - day 6 → email `balance_reminder_d6`;
  - day ≤ 5 → auto-cancel (`cancel_reason='balance_unpaid'`). Never cancel if a balance payment is `processing`/`succeeded` in Stripe.
- The pre-trip reminder pause (`reminders_paused`) does NOT stop the deposit sweep.
- The sweep includes `is_test=true` bookings only when `isStripeTestMode()` is true.
- `DEPOSIT_TERMS_VERSION = '2026-11-26'`. The server rejects a deposit without `deposit_ack: {accepted:true, version}`.
- The browser never sends amounts. Every amount comes from the booking row or the pricing engine.
- Balance-link token:
  - HMAC-SHA256 with `QR_SIGNING_SECRET`, domain-separated with the prefix `'balance:'`;
  - sent in the URL fragment: `PUBLIC_SITE_URL + '/saldo#t=' + token`;
  - must contain no name, email or amount.
- Files are CRLF (renormalize after edits). Keep new files under 500 lines. No `Co-Authored-By` trailer.
- Migration 0028 goes to Preview first, then to Production **before** the merge. Merge to `main` only with explicit owner OK.
- Bump the cache-busters for every changed public asset (`app.js?v=hp10` → `hp11`, `content.js?v=hp10` → `hp11`) on every page that loads them.
- Copy is bilingual (EN/ES). Use high-contrast dark text on light cards.

## Review Focus

1. **Plan or date changes after a PaymentIntent exists.** If the customer switches full↔deposit (or changes
   the date) on the same `request_id`, it must not be double-charged. Expect a fresh `request_id` on the
   client and `409 REQUEST_ID_CONFLICT` on the server. → Task 4 test `mismatch on payment_plan`.
2. **Race at the deadline.** The customer pays the balance while the sweep cancels. The sweep skips when the
   balance PI is `processing`/`succeeded`. A balance success after cancellation sets `needs_review_reason`
   and emails the owner, and never reactivates by itself. → Task 6 and Task 7 tests.
3. **30/31-day boundary near midnight UTC.** Eligibility uses Galápagos "today": 31 days → eligible, 30 → not.
   → Task 1 test `boundary 30/31`.
4. **Rounding.** Odd totals split exactly (deposit + balance == total), e.g. 33333 → 10000 + 23333 and
   19500 → 5850 + 13650. → Task 1 test.
5. **Foreign Stripe events.** On the shared account's TEST webhook, events from other projects (no booking,
   or another tenant in metadata) return 200 ignored, never 500. → Task 6 test.
